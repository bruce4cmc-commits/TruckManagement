# 卡車管理系統－流程與管理方式 V1.2（Supabase Direct）

## 1. 文件目的

本文件整併目前已確認之卡車管理系統需求，作為後續畫面設計、Supabase PostgreSQL 資料庫設計、Supabase REST/PostgREST、RLS/RPC 與 Web App 開發之基礎。

本版僅定義：
- 運輸作業流程
- 使用角色與權限
- 車趟計畫管理方式
- QR Code 回報方式
- 異常與人工補正規則
- 即時車況管理方式
- KPI 定義

**本版不包含 Supabase 資料庫欄位設計。**


本版系統基礎：
- 前端：HTML / CSS / JavaScript Web App
- 資料庫：Supabase PostgreSQL（REST/PostgREST）
- 司機端：手機 Web App
- 物流管理端：手機 / PC Web
- 主管端：PC / 平板 Dashboard
- 不使用 GPS

> 技術實作說明：移除 Google Apps Script 後，瀏覽器端使用 Supabase Publishable key 存取 Data API；登入與身分識別使用 Supabase Auth，資料授權由 PostgreSQL RLS 控制。複雜且需一致性之寫入邏輯可使用 PostgreSQL Function / RPC，定時工作使用 Supabase Cron。Secret key / service_role 不得放入瀏覽器。

## 2. 系統定位

系統名稱：**楊梅廠－新竹廠卡車循環運輸管理系統**

系統目的：
- 管理楊梅廠與新竹廠之間的循環運輸車趟。
- 以 QR Code／手機 Web App 回報作業節點。
- 不使用 GPS 追蹤。
- 由物流人員預先設定週間車趟計畫。
- 即時掌握每台車目前所處作業節點與異常狀態。
- 比較計畫與實績。
- 提供主管日／週／月 KPI。

系統核心管理對象：
- 時間
- 趟次
- 車輛
- 司機
- 作業節點
- 計畫與實績差異
- 異常
- KPI

本系統**不管制每趟車頭／引擎裝載數量**。

## 3. 工廠與運輸背景

### 3.1 工廠
- 楊梅廠
- 新竹廠

### 3.2 運輸目的
新竹廠生產所需物料由楊梅廠供應，卡車於兩廠之間進行循環運輸。

### 3.3 運輸特性
- 固定廠際循環運輸。
- 不使用 GPS。
- 司機透過手機 Web App 掃描各節點 QR Code。
- 每一完整 Cycle 標準時間為 **120 分鐘**。
- 每一 Trip 由同一台卡車完成完整作業流程。
- Trip 不跨日。
- 星期日不排程。
- 星期六沿用平日班表邏輯。

## 4. 使用者角色

### 4.1 司機（外聘）
使用裝置：手機 Web App

主要功能：
- 固定網址登入。
- 以「車號 + 密碼」方式登入。
- 原則上一車一司機。
- 臨時代班時允許司機自行選車。
- 掃描各作業節點 QR Code。
- 接收超時／異常手機通知。
- 回報交通異常。

限制：
- 不使用 GPS。
- 不提供一般手動完成按鈕；正常作業必須使用 QR Code 回報。

### 4.2 物流管理人員
使用裝置：手機 Web App、PC Web

主要功能：
- 設定週間車趟計畫。
- 修改未執行車趟。
- 追加／取消車趟。
- 指定／修改車輛與司機。
- 查看即時車況。
- 接收異常通知。
- 人工補登漏掃時間。
- 更正已完成 Trip 資料。
- 查看日／週／月執行狀況。

### 4.3 物流主管
使用裝置：PC／平板 Web Dashboard

主要功能：
- 查看所有車輛即時狀態。
- 查看日／週／月 KPI。
- 查看計畫與實績差異。
- 查看異常趨勢。
- 查看各車運輸趟次與效率。

## 5. 完整運輸 Cycle 定義

完整 Cycle 定義為：

> **本次楊梅廠出廠 → 同一台車下一次楊梅廠出廠**

標準 Cycle Time：**120 分鐘**

Cycle KPI 準時判定：

> **Cycle Time ≤ 140 分鐘視為準時。**

提早完成 Cycle 不視為異常。

## 6. 標準作業流程

### 6.1 完整時間鏈
以 09:00 楊梅出廠為例：

```text
楊梅出廠        09:00
↓ +30分鐘
新竹入廠        09:30
↓ +5分鐘
新竹車頭庫房    09:35
↓ +25分鐘
新竹出廠        10:00
↓ +30分鐘
楊梅入廠        10:30
↓ +5分鐘
楊梅卸引擎      10:35
↓ +10分鐘
楊梅裝車頭      10:45
↓ +15分鐘
下一趟楊梅出廠  11:00
```

合計：**120 分鐘**

### 6.2 管制節點

| NO | 管制節點 | 地點 | 完成後狀態 | 標準時間 |
|---:|---|---|---|---:|
| 1 | 楊梅廠出發 | 楊梅廠門口 | 楊梅→新竹跨廠移動中 | 30 分鐘 |
| 2 | 新竹廠抵達 | 新竹廠門口 | 新竹廠內移動中 | 5 分鐘 |
| 3 | 新竹廠卸貨／裝貨 | 新竹車頭庫房 | 卸車頭／裝引擎中 | 25 分鐘 |
| 4 | 新竹廠出發 | 新竹廠門口 | 新竹→楊梅跨廠移動中 | 30 分鐘 |
| 5 | 楊梅廠抵達 | 楊梅廠門口 | 楊梅廠內移動中 | 5 分鐘 |
| 6 | 楊梅廠卸貨 | 楊梅引擎庫房 | 引擎卸貨中 | 10 分鐘 |
| 7 | 楊梅廠裝貨 | 楊梅車頭庫房 | 車頭裝載中／待出廠 | 15 分鐘 |
| →1 | 下一趟楊梅廠出發 | 楊梅廠門口 | 下一 Cycle 開始 | — |

## 7. QR Code 管理方式

### 7.1 QR Code 原則
- 每個管制節點各自設置一張 QR Code。
- 不共用不同節點 QR Code。
- 司機到達節點後，以手機 Web App 掃描。
- 系統依掃描結果記錄實際完成時間。
- 系統依目前流程狀態自動切換到下一作業狀態。
- 司機不需自行選擇目前車輛狀態。

### 7.2 QR Code 設置地點
- 楊梅廠門口－出廠
- 新竹廠門口－入廠
- 新竹車頭庫房
- 新竹廠門口－出廠
- 楊梅廠門口－入廠
- 楊梅引擎庫房
- 楊梅車頭庫房

---

## 8. QR 漏掃、重複掃描與補正

### 8.1 漏掃
- 不阻擋後續節點繼續掃描。
- 漏掃節點在管理畫面顯示警示。
- 該筆節點紀錄保留缺漏狀態。
- 物流管理人員可人工補登時間。
- 人工補登資料需標記為「人工補正」。
- 人工補正不要求輸入原因。

### 8.2 重複掃描
- 同一節點重複掃描時，原則上只採用首筆有效紀錄。
- 若與前次相同節點掃描時間相隔超過 **100 分鐘**，可視為下一趟 Cycle 的節點回報。

### 8.3 已完成 Trip 更正
物流管理人員可以更正已完成 Trip，但：
- 不直接覆蓋原始 QR 掃描紀錄。
- 原始時間需保留。
- 系統另外保存／顯示更正後時間。
- KPI 應以有效更正後資料計算。
- 管理畫面需能辨識資料曾經人工更正。

---

## 9. 無網路處理方式

若司機掃描 QR Code 時手機暫時無網路：
- Web App 暫存回報資料於手機端。
- 網路恢復後自動／提示補傳。
- 補傳時保留實際掃描時間，不以補傳時間取代實際作業時間。

## 10. 異常管理

### 10.1 交通異常分類
1. 塞車
2. 事故
3. 車故障
4. 其它

### 10.2 節點超時警示
各節點依標準時間管理：

> **超過該節點標準時間 15 分鐘即產生警示。**

例如楊梅→新竹標準30分鐘，超過45分鐘仍未完成新竹入廠掃碼，即顯示超時。

### 10.3 異常顯示與通知
異常發生時：
- 管理畫面顯示。
- 手機通知。

通知對象：
- 該車司機
- 物流管理人員

手機通知可設定開啟／關閉。

### 10.4 異常解除
當司機完成下一節點 QR Code 回報時，自動解除該節點的進行中異常狀態；異常歷史紀錄仍保留。

## 11. 週間車趟計畫管理

### 11.1 設定責任
由**物流管理人員**負責建立與維護。

### 11.2 設定週期
- 每次輸入一週計畫。
- 星期一～星期六可排程。
- 星期六沿用平日班表。
- 星期日不排程。
- 計畫可隨時修訂。

### 11.3 排程格式
採：

> **每天一列一趟**

每一趟由物流人員設定：
- 日期
- 趟次
- 楊梅計畫出廠時間
- 車輛

司機原則上由車輛自動帶出，但允許臨時調整。

不需設定：
- 車頭數量
- 引擎數量

### 11.4 計畫時間基準
所有週間計畫：

> **以楊梅廠出廠時間為排程基準。**

例如設定09:00楊梅出廠，系統可推算：
- 新竹入廠：09:30
- 新竹車頭庫房：09:35
- 新竹出廠：10:00
- 楊梅入廠：10:30
- 楊梅卸引擎：10:35
- 楊梅裝車頭：10:45
- 下一次該車可出發：11:00

## 12. 每日班表與車輛配置

### 12.1 車輛數量
目前啟用車輛：**2 台**

系統需支援：
- 增加車輛
- 停用車輛
- 恢復啟用車輛

有歷史資料之車輛不建議直接刪除。

### 12.2 每日趟數
兩台車時：
- 每日通常約 **7～10趟**
- 依需求調整
- 既有班表模板可支援07:00起、每小時一趟、最晚18:00出發
- 若未來增加卡車數量，班表需可調整

## 13. 車輛交錯排程原則

兩台車時採交錯排程，例如：

```text
07:00 車01
08:00 車02
09:00 車01
10:00 車02
11:00 車01
...
```

若當日車01跑首趟，且當日總Trip數為奇數，則車01當日會多跑一趟，因此**次日首趟由車02開始**，以平衡兩台車累積執行趟次。

系統應：
- 自動提出建議車號。
- 保留物流管理人員手動修改彈性。
- 未來車輛數增加時可擴充。

---

## 14. 車輛排程衝突檢查

由於標準 Cycle 為120分鐘，同一台車原則上不得被安排在上一趟尚未完成時再次出發。

例如：
- 車01 09:00出發
- 下一個標準可出發時間為11:00

若又安排車01於10:00出發，系統應顯示排程衝突警告。

物流管理人員仍保有特殊情況下手動調整能力。

---

## 15. 計畫出發準時判定

楊梅廠計畫出發時間允許誤差：

> **±20分鐘**

| 計畫時間 | 實際出發 | 判定 |
|---|---|---|
| 09:00 | 08:45 | 準時 |
| 09:00 | 09:12 | 準時 |
| 09:00 | 09:20 | 準時 |
| 09:00 | 09:21 | 延遲 |
| 09:00 | 08:39 | 過早 |

KPI：

> **楊梅出發準時率 = 實際楊梅出廠落於計畫時間 ±20分鐘內之Trip ÷ 實際執行Trip**

---

## 16. 臨時追加 Trip

物流人員可於週間計畫發布後隨時追加 Trip。

追加 Trip 必須填寫原因：
1. 庫存調整（增加）
2. 額外零件運輸需求
3. 車輛調度
4. 其它

規則：
- 保留「臨時追加」標記。
- 不可將已開始執行的既有 Trip 改成另一個 Trip。
- 已執行中的 Trip 若有額外需求，應另外新增 Trip。
- 新增時執行車輛時間衝突檢查。

---

## 17. 取消 Trip

物流人員可取消尚未執行之 Trip。

取消必須填寫原因：
1. 庫存調整（減少）
2. 車輛異常
3. 其它

規則：
- 取消 ≠ 刪除。
- 被取消 Trip 必須保留在歷史計畫中。
- 主管可查看原計畫、取消與最終執行結果。

---

## 18. 計畫修訂規則

### 18.1 尚未開始
允許：
- 修改出發時間
- 更換車輛
- 更換司機
- 取消
- 新增／追加 Trip

### 18.2 已開始
不允許：
- 刪除 Trip
- 將該 Trip 直接改成另一趟

允許：
- 更換車輛／司機資訊
- 異常註記
- 修訂後續未開始計畫

### 18.3 已完成
允許物流管理人員更正，但：
- 原始 QR 紀錄必須保留。
- 系統需另記更正結果。
- 不得直接消除原始紀錄。

## 24. V1 KPI

第一版採以下10項 KPI：

1. **計畫 Trip 數**：該期間原訂應執行之 Trip 數。
2. **實際完成 Trip 數**：實際完成完整 Cycle 之 Trip 數。
3. **Trip 達成率**：實際完成 Trip ÷ 最終計畫 Trip × 100%。
4. **楊梅出發準時率**：實際楊梅出廠落於計畫時間 ±20分鐘之 Trip 比例。
5. **平均完整 Cycle Time**：同一車本次楊梅出廠至下一次楊梅出廠之平均時間。
6. **Cycle 準時率**：Cycle Time ≤140分鐘之比例。
7. **異常 Trip 數／異常率**：節點超時、漏掃、交通異常等 Trip 數及比例。
8. **追加 Trip 數**：原週間計畫發布後臨時追加之 Trip。
9. **取消 Trip 數**：原計畫後取消之 Trip。
10. **各車完成 Trip 數**：依車輛統計日／週／月完成趟次。

## 26. 系統管理核心原則

1. 以週間計畫為基礎。
2. 以楊梅出廠時間作為排程時間基準。
3. 以 QR Code Event 作為實際作業依據。
4. 不使用 GPS。
5. 每一 Trip 由同一台車完成完整流程。
6. 完整 Cycle 標準120分鐘。
7. Cycle ≤140分鐘視為準時。
8. 各節點超過標準時間15分鐘即警示。
9. 楊梅計畫出發時間允許 ±20分鐘。
10. 漏掃不阻擋後續流程，但必須警示。
11. 人工補正必須留下標記。
12. 原始 QR 紀錄不可因人工修正而消失。
13. 取消 Trip 不可直接刪除。
14. 追加 Trip 必須記錄追加原因。
15. 取消 Trip 必須記錄取消原因。
16. 車輛原則上採交錯排程，但保留人工調整能力。
17. 系統需支援未來增加／停用車輛。
18. 不管理車頭與引擎實際裝載數量。
