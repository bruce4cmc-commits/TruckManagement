# 卡車管理系統－Wireframe V1.2（Supabase Direct）

## 1. 文件目的

本文件彙整「卡車管理系統」目前已確認之 Wireframe 畫面與操作規格，作為後續 System Flow、Supabase 資料結構、Supabase REST/PostgREST、RLS/RPC 與 Web App 開發之介面依據。

本文件涵蓋三類使用者：

1. 司機
2. 物流管理人員
3. 物流主管

本版僅定義畫面、操作與顯示邏輯，**不包含 Supabase 資料庫欄位設計**。


本版系統基礎：
- 前端：HTML / CSS / JavaScript Web App
- 資料庫：Supabase PostgreSQL（REST/PostgREST）
- 司機端：手機 Web App
- 物流管理端：手機 / PC Web
- 主管端：PC / 平板 Dashboard
- 不使用 GPS

> 技術實作說明：移除 Google Apps Script 後，瀏覽器端使用 Supabase Publishable key 存取 Data API；登入與身分識別使用 Supabase Auth，資料授權由 PostgreSQL RLS 控制。複雜且需一致性之寫入邏輯可使用 PostgreSQL Function / RPC，定時工作使用 Supabase Cron。Secret key / service_role 不得放入瀏覽器。

# 2. 共通設計原則

## 2.1 系統平台
- 司機：手機 Web App
- 物流管理人員：手機 Web App／PC Web
- 物流主管：PC／平板 Web Dashboard

## 2.2 即時狀態來源
本系統不使用 GPS。

即時車況依據：

> **每台車最後一筆有效 QR Code 回報紀錄**

進行判斷。

## 2.3 狀態顏色
- 綠色：正常
- 黃色：接近超時
- 紅色：異常／超時
- 藍色：廠內作業
- 灰色：尚未開始

## 2.4 QR Code 原則
- 每個管制節點各自一張 QR Code。
- 掃描成功後不需二次確認。
- 掃描後自動記錄時間。
- 掃錯 QR Code 時警示，但允許司機確認後繼續。
- 漏掃不阻擋後續流程。
- 漏掃不列為異常 Trip。
- 漏掃不進異常中心。
- 漏掃不發送異常通知。
- 物流管理人員仍可選擇人工補正。

# 3. 司機端 Wireframe

司機端 V1 共包含 6 個主要畫面：

1. 登入
2. 首頁
3. QR Code 掃描
4. 回報結果
5. 交通異常回報
6. 今日任務

## 3.1 登入畫面

### 顯示內容
- 系統名稱
- 車號
- 密碼
- 登入按鈕

### 操作邏輯
- 使用固定網址進入。
- 司機選擇車號。
- 輸入密碼。
- 驗證成功後進入首頁。
- 原則上一車一司機。
- 臨時代班時允許司機自行選車。
- 物流管理人員可重設司機密碼。

## 3.3 QR Code 掃描畫面

### 顯示內容
- 相機掃描區
- 預期下一節點
- 操作提示

### 操作邏輯
- 掃描成功後直接成立。
- 不需二次確認。

- 系統自動判斷節點與更新狀態。

若掃描節點與系統預期不一致：
- 顯示預期節點。
- 顯示實際掃描節點。
- 警示可能漏掃。
- 不阻擋司機繼續。
- 司機可返回重新掃描，或確認本次回報。

```text
┌─────────────────────────────┐
│         ⚠ 作業提醒           │
├─────────────────────────────┤
│ 預期節點：                   │
│ 新竹廠入廠                   │
│                             │
│ 本次掃描：                   │
│ 新竹廠出廠                   │
│                             │
│ 中間可能有節點漏掃。          │
│                             │
│ [ 返回重新掃描 ]              │
│ [ 確認本次回報 ]              │
└─────────────────────────────┘
```

## 3.5 掃描成功畫面
- 顯示回報成功、節點名稱、掃描時間、下一節點。
- 顯示數秒後自動返回首頁。

```text
┌─────────────────────────────┐
│            ✓                │
│         回報成功             │
│                             │
│ 新竹廠入廠                   │
│ 09:31                       │
│                             │
│ 下一作業：                   │
│ 新竹車頭庫房                 │
└─────────────────────────────┘
```

## 3.6 超時顯示
司機需看到：標準時間、警示時間、已耗時、超時分鐘數。

## 3.7 交通異常回報
異常分類：
1. 塞車
2. 事故
3. 車故障
4. 其它

備註為選填。

## 3.8 今日任務
司機可查看當日該車全部預定 Trip，包括計畫時間、Trip 次序、狀態。

## 3.9 出發前提醒
系統需提供出發前提醒，建議預設為**計畫出發前10分鐘**，且可由使用者自行開啟／關閉。

# 4. 物流管理人員端 Wireframe

物流管理端 V1 共包含 9 個主要畫面：
1. 今日車況
2. 車輛詳情
3. 週間車趟計畫
4. Trip 編輯
5. 今日計畫 vs 實績
6. 異常中心
7. 人工補正／更正
8. 車輛／司機管理
9. 通知設定

## 4.1 今日車況首頁
每台車以卡片顯示：車號、司機、今日第幾趟、目前狀態、最後回報、已耗時、下一節點、下一計畫、延遲分鐘數、異常狀態。

## 4.2 車輛詳情
顯示單一 Trip 七個節點、實際完成時間、預計時間、警示時間、目前節點、下一節點。

**不顯示每個節點「計畫 vs 實際差異」。**

## 4.3 週間車趟計畫
- 每次設定一週計畫。
- 星期一～星期六。
- 星期日不排程。
- 採「每天一列一趟」。
- 支援複製上週。
- 不需要複製單一天功能。

顯示欄位：日期、趟次、計畫出發、建議車輛、實際／指定車輛、司機、類型、狀態。

## 4.4 車輛自動排程
兩台車時，系統預設自動套用交錯排程，物流管理人員可手動修改。

若當日為奇數趟，隔日首車自動交換。

## 4.5 排程衝突
若同一台車在前一 Cycle 尚未完成前再次被安排出發：
- 顯示警告。
- 允許物流管理人員強制儲存。

## 4.6 新增 Trip
輸入內容：日期、楊梅計畫出發時間、車輛、司機、類型。

Trip 編號由系統自動產生。

## 4.7 追加 Trip
追加原因必填：
1. 庫存調整（增加）
2. 額外零件運輸需求
3. 車輛調度
4. 其它

追加 Trip 需保留「臨時追加」標記。

## 4.8 取消 Trip
取消原因必填：
1. 庫存調整（減少）
2. 車輛異常
3. 其它

取消不等於刪除，需保留於歷史計畫。

## 4.9 已開始 Trip
不允許：刪除、改成另一趟、更換車輛。

允許：異常註記、修訂後續未開始計畫。

## 4.10 人工補正
- 適用 QR 漏掃。
- 可人工補登時間。
- 顯示「人工補正」標記。
- 不需輸入原因。
- 非強制補正。

## 4.11 已完成 Trip 更正
- 物流管理人員可更正。
- 原始 QR 時間保留。
- 另存更正後有效時間。
- KPI 以更正後時間計算。

## 4.12 異常中心
列入：節點超時、塞車、事故、車故障、其它交通／運輸異常。

不列入：單純漏掃 QR。

## 4.13 今日計畫 vs 實績
顯示：趟次、計畫、實際出發、車號、狀態、差異。

## 4.14 車輛／司機管理
功能：新增車輛、停用車輛、恢復啟用、指定固定司機、重設司機密碼。

有歷史資料之車輛不直接刪除。

## 4.15 通知設定
採每位使用者自行設定，可開啟／關閉：超時通知、交通異常通知、出發前提醒。

漏掃不通知。

# 5. 物流主管端 Wireframe

主管端 V1 共包含 4 個主要畫面：
1. Dashboard 首頁
2. KPI 分析
3. 異常分析
4. Trip 歷史

## 5.1 Dashboard 首頁
顯示核心 KPI：
- 計畫 Trip
- 完成 Trip
- Trip 達成率
- 出發準時率
- 平均 Cycle Time
- Cycle 準時率
- 異常 Trip
- 追加 Trip
- 取消 Trip

並顯示：即時車況、橫式流程進度、今日計畫 vs 實績、趨勢圖。

## 5.2 日／週／月切換
所有 KPI 與圖表支援日、週、月切換，切換期間後同步更新。

## 5.3 即時車況
主管看到：車號、司機、今日第幾趟、目前狀態、最後回報、已耗時、下一計畫、延遲分鐘、異常狀態。

不顯示司機電話或其它聯絡個資。

## 5.4 橫式流程進度條
主管端保留橫式表示：

```text
車01｜第5趟｜王先生

楊梅出廠   新竹入廠   新竹庫房   新竹出廠   楊梅入廠   卸引擎   裝車頭
   ●────────●────────◉────────○────────○────────○────────○
 11:03     11:34      目前
```

圖示：
- ● 已完成
- ◉ 目前階段
- ○ 尚未完成
- 🔴 超時

## 5.5 今日計畫 vs 實績
主管唯讀，顯示趟次、計畫、實際、車號、Cycle、狀態。

# 6. V1 KPI 顯示規格

第一版確認採以下 10 項 KPI：
1. 計畫 Trip 數
2. 實際完成 Trip 數
3. Trip 達成率
4. 楊梅出發準時率
5. 平均完整 Cycle Time
6. Cycle 準時率
7. 異常 Trip 數／異常率
8. 追加 Trip 數
9. 取消 Trip 數
10. 各車完成 Trip 數

## 6.1 KPI 判定標準
- 出發準時率：實際楊梅出廠時間落於計畫時間 **±20分鐘**。
- 平均 Cycle Time：同一台車本次楊梅出廠 → 下一次楊梅出廠，標準 **120分鐘**。
- Cycle 準時率：**Cycle Time ≤140分鐘**。
- 節點超時：**標準時間 +15分鐘**。
- 異常 Trip 包含節點超時、塞車、事故、車故障、其它交通／運輸異常；**不包含漏掃 QR Code**。

# 9. Wireframe V1.2 定版原則

1. 司機登入統一使用「車號 + 密碼」。
2. QR 掃描成功後不二次確認。
3. 掃錯 QR 警示但不阻擋。
4. 成功回報後自動返回首頁。
5. 司機端保留完整今日任務。
6. 司機端顯示超時分鐘數。
7. 司機端加入出發前提醒。
8. 物流端週間計畫採每天一列一趟。
9. 兩車交錯排程預設自動套用。
10. 物流人員可人工修改車輛配置。
11. 排程衝突警示後可強制儲存。
12. Trip 編號由系統自動產生。
13. 已開始 Trip 不允許換車。
14. 已開始 Trip 不允許刪除或改成別趟。
15. 漏掃不列為異常 Trip。
16. 漏掃不進異常中心。
17. 漏掃不發送通知。
18. 漏掃保留人工補正能力。
19. 人工補正不需原因。
20. 已完成 Trip 更正需保留原始 QR 時間。
21. 車輛管理需提供司機密碼重設。
22. 通知設定由每位使用者各自管理。
23. 主管不顯示司機聯絡資訊。
24. 主管流程進度採橫式表示。
25. V1 趨勢圖全部保留。
26. 不使用 GPS。
27. 不管理車頭／引擎裝載數量。
